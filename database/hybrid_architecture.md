# KFM-AE Hybrid Database Architecture\n\nThis document outlines the hybrid database architecture used in the KFM-Agentic Evolution (KFM-AE) system, combining PostgreSQL and Neo4j to leverage the strengths of both relational and graph databases.\n\n## 1. Rationale\n\nThe KFM-AE system needs to manage both structured core data about agentic entities (like ID, type, version, lifecycle state) and complex, potentially deeply nested relationships between them (dependencies, evolution lineage). A single database type struggles to efficiently handle both requirements:\n\n*   **PostgreSQL (Relational):** Excels at storing structured data with strong consistency (ACID compliance) and enforcing relational integrity. Ideal for the core agent registry and the immutable state transition log.\n*   **Neo4j (Graph):** Natively designed for modeling and querying complex relationships. Ideal for representing and analyzing agent dependencies, lineage, and compositions, enabling efficient multi-hop traversals and pattern detection.\n\nBy combining these, we achieve a robust and performant architecture where each database handles the tasks it's best suited for.\n\n## 2. Database Responsibilities\n\n*   **PostgreSQL:**\n    *   Master store for core agent entity data (`Agents` table).\n    *   Master store for flexible agent metadata (`AgentMetadata` table using JSONB).\n    *   Immutable log of all agent lifecycle state transitions (`StateTransitionLog` table).\n    *   Enforces relational integrity for core agent data.\n\n*   **Neo4j:**\n    *   Master store for relationships between agents (`:DEPENDS_ON`, `:EVOLVED_FROM`, `:COMPOSED_OF`, `:EXTENDS` relationships).\n    *   Stores a *synchronized copy* of key agent properties on `:Agent` nodes (`unique_id`, `type`, `version`, `status`) to facilitate efficient graph traversals without needing to constantly join back to PostgreSQL.\n    *   Used for queries involving relationship traversal, pathfinding, impact analysis, lineage tracking, and complex pattern detection (e.g., circular dependencies).\n\n## 3. Synchronization Strategy\n\nMaintaining consistency between the PostgreSQL `Agents` table and the Neo4j `:Agent` nodes is crucial. We employ an event-driven strategy using database triggers, a message queue, and a dedicated synchronization service:\n\n**Flow:** `PostgreSQL (Trigger) -> pg_notify -> MQ Listener -> Message Queue (e.g., RabbitMQ) -> Sync Service -> Neo4j (Cypher)`\n\n1.  **PostgreSQL Triggers:**\n    *   An `AFTER INSERT OR UPDATE` trigger on the `Agents` table captures changes to agent data.\n    *   An `AFTER DELETE` trigger captures agent deletions.\n    *   These triggers format a JSON payload containing the operation type (`INSERT`, `UPDATE`, `DELETE`) and relevant agent data (key properties for insert/update, `unique_id` for delete).\n    *   The payload is sent asynchronously using `pg_notify` to a dedicated channel (e.g., `agent_sync_channel`).\n\n2.  **Message Queue Listener / Broker:**\n    *   A lightweight listener process connects to PostgreSQL and uses `LISTEN agent_sync_channel`.\n    *   Upon receiving a notification, it retrieves the JSON payload.\n    *   It publishes the payload as a message to a durable Message Queue (e.g., a RabbitMQ exchange/queue configured for persistence). This decouples PostgreSQL from the sync logic and adds resilience.\n\n3.  **Synchronization Service (Microservice):**\n    *   This service consumes messages from the Message Queue.\n    *   **On `INSERT`/`UPDATE` Message:** It executes an idempotent `MERGE` Cypher command in Neo4j. This command finds an `:Agent` node based on `unique_id` or creates it if it doesn't exist, then sets its properties (`type`, `version`, `status`) based on the message payload. It also ensures the correct secondary label (e.g., `:AIModel`) is applied.\n    *   **On `DELETE` Message:** It executes a `MATCH (a:Agent {unique_id: $id}) DETACH DELETE a` Cypher command to remove the corresponding node and all its relationships from Neo4j.\n\n## 4. Error Handling\n\nSynchronization failures can occur (e.g., temporary network issues, Neo4j unavailability). The Sync Service implements:\n\n*   **Retry Logic:** Transient errors trigger automatic retries with exponential backoff (e.g., 3 attempts).\n*   **Dead-Letter Queue (DLQ):** If retries fail, the problematic message is moved to a dedicated DLQ in the message broker.\n*   **Monitoring & Alerting:** The DLQ depth is monitored, and alerts are raised if messages accumulate, indicating persistent sync issues requiring manual investigation and potential message replay.\n\n## 5. Consistency Monitoring\n\nWhile the sync mechanism aims for eventual consistency, periodic checks verify data integrity:\n\n*   **Scheduled Job:** Runs periodically (e.g., hourly/daily).\n*   **Checks Performed:**\n    *   Compares the total count of rows in the PostgreSQL `Agents` table with the count of `:Agent` nodes in Neo4j.\n    *   Selects a random sample of agents from PostgreSQL and verifies that their key properties (`type`, `version`, `status`) match the properties of the corresponding node in Neo4j.\n*   **Alerting:** Discrepancies trigger alerts for investigation.
